# ADR 0038: Resource-First API Taxonomy, Zero-DB Head Hydration, and Storage Source Transparency

## Context and Problem Statement

During integration testing of downstream client applications (e.g. `ed-integration-smoke`, copilot overlays, and annunciator dashboards), four critical integration friction points emerged regarding `ed_telemetry.adapters.driving.api.server.HttpApiAdapter`:

1. **Unreliable "New" Content & Hybrid Inconsistency on `/telemetry/head`:**
   `/api/v1/telemetry/head` (ADR 0036, ADR 0037) aggregated instantaneous disk caches (`Status.json`, auxiliary snapshots) with a fallback SQLite database query for `latest_journal_event`. This created an architectural anti-pattern:
   * When historical archives were backfilled into SQLite, auto-incrementing database IDs caused old historical events to masquerade as the "latest active" event.
   * Coupling in-memory disk caching with SQLite WAL read locks made head-state inspection latency unpredictable.
   * Callers had no clear signal of whether state had changed without performing expensive client-side JSON diffs.
2. **Confusing and Counterintuitive Endpoint Paths:**
   The v1 URL namespace lacked consistent resource semantics:
   * `/api/v1/status` (ingestion thread state) conflicted conceptually with `/api/v1/status/game` (in-game cockpit state).
   * `/api/v1/events` was vague: it queried historical SQLite rows, whereas `/api/v1/events/buffer` destructively drained an in-memory queue.
   * `/api/v1/stream` was placed at the root level rather than within an event resource hierarchy.
   * `/api/v1/control/watch` used an RPC-style action verb in the URL path.
3. **Data Source Ambiguity (In-Memory Buffer vs. SQLite DB):**
   Callers could not determine whether an endpoint accessed transient memory buffers, direct disk caches, or durable SQLite storage. This led to misconceptions regarding query performance, persistence durability, and side effects.
4. **Cold-Start Replay vs. Model State Hydration:**
   Callers maintaining domain models need all current state populated immediately upon connection without racing through thousands of historical journal entries. Yet they need to be confident that `ed-telemetry`'s pure boundary (an agnostic telemetry pipeline, not a game-state business engine) is strictly preserved.

How should `ed-telemetry` structure its driving HTTP interface to provide clean resource paths, transparent data-source attribution, 100% in-memory state hydration, and CI-enforceable architectural compliance?

---

## Decision Drivers

* **Zero-DB State Hydration:** Full instantaneous state hydration (`/telemetry/head`) must be served 100% from in-memory disk caches with zero SQLite queries, completely immune to historical backfill distortion.
* **Resource-First REST Naming:** Align routes strictly with the natural telemetry artifacts generated by *Elite Dangerous*: `/status` (`Status.json`), `/snapshots/*` (auxiliary state dumps), `/journal/*` (append-only logs), and `/system/*` (daemon infrastructure).
* **Storage Source Transparency:** Every response must explicitly declare its storage tier via HTTP headers (`X-Telemetry-Source: memory-buffer | sqlite-wal`).
* **Non-Breaking Path Evolution:** Maintain legacy `/api/v1/*` paths as deprecated aliases to preserve compatibility with existing integrations.
* **CI-Enforceable Architectural Quality Gates:** Formulate explicit path and header conventions that are automatically verified by `pytest`, `pre-commit`, and the verification pipeline.

---

## Decision Outcome

Chosen Option: **Adopt Clean Resource-First API Taxonomy with 100% In-Memory State Hydration and Automated CI Governance**.

### 1. Clean Resource-First Canonical Endpoint Table

| Canonical Endpoint | HTTP Method | Data Source | Source File / Scope | Legacy Route (Deprecated Alias) | Role & Behavior |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **`/api/v1/state`** | `GET` | **In-memory cache only** | All (`Status.json`, snapshots, active journal tail) | `/api/v1/telemetry/head` | **Full State Hydration.** Returns instantaneous cockpit state, all active snapshots, and active journal tail with zero database queries. |
| **`/api/v1/status`** | `GET` | **In-memory cache** | `Status.json` | `/api/v1/status/game` | Returns active cockpit telemetry payload, bitflags, and raw SHA-256 hash. |
| **`/api/v1/snapshots/{name}`** | `GET` | **In-memory cache** | `Market.json`, `Cargo.json`, etc. | — | Returns raw payload and hash of a specific auxiliary snapshot by name (e.g. `/snapshots/market`). |
| **`/api/v1/snapshots`** | `GET` | **In-memory cache** | All registered snapshot files | — | Returns a dictionary containing all currently active auxiliary snapshots in a single call. |
| **`/api/v1/journal/latest`** | `GET` | **In-memory tail** | Active `Journal.*.log` | — | Returns the single most recent journal event read directly from the active file tail. |
| **`/api/v1/journal/query`** | `GET` | **SQLite DB (WAL)** | Persisted events | `/api/v1/events` | Filtered historical search over persisted events. Supports query parameters: `topic`, `since_id`, `limit`, and `order`. |
| **`/api/v1/journal/stream`** | `GET` | **Stream generator** | Live events | `/api/v1/stream` | Continuous Server-Sent Events (SSE) feed. Supports optional `?topics=journal,status` filter. |
| **`/api/v1/journal/queue`** | `GET` | **In-memory ring buffer** | Ingestion queue | `/api/v1/events/buffer` | Destructively drains and returns queued events from the in-memory ring buffer (deprecated). |
| **`/api/v1/system/health`** | `GET` | **In-memory** | N/A | `/api/v1/health` | Daemon liveness check probe (`{"status": "ok"}`). |
| **`/api/v1/system/watcher`** | `GET` | **In-memory** | N/A | `/api/v1/status` (old semantics) | Telemetry watcher operational metrics: running state, poll interval, monitored directory. |
| **`/api/v1/system/logs`** | `GET` | **In-memory buffer** | N/A | `/api/v1/diagnostics/logs` | Retrieves diagnostic application log entries from the ring buffer (`min_level`, `limit`). |
| **`/api/v1/system/control`** | `POST` | **Reactor thread** | N/A | `/api/v1/control/watch` | Controls ingestion thread lifecycle (`{"action": "start"\|"stop"}`). |

### 2. Architectural Invariants

* **Invariant 1 (Zero-DB Head Hydration):** `/api/v1/state` (and legacy `/api/v1/telemetry/head`) must resolve `latest_journal_event` exclusively from the active in-memory journal tail reader (`WatcherPort.read_active_journal_tail()`). It must **never** execute fallback SQL queries against `TelemetryRepositoryPort`. If no journal file is actively open, `latest_journal_event` must return `null`.
* **Invariant 2 (Source Transparency Headers):** Every HTTP response emitted by `HttpApiAdapter` must include:
  * `X-Telemetry-Source: memory-buffer` for in-memory and disk-cached responses (`/state`, `/status`, `/snapshots/*`, `/journal/latest`, `/journal/queue`, `/system/*`).
  * `X-Telemetry-Source: sqlite-wal` for database queries (`/journal/query`).
  * `X-Telemetry-Plane: state | status | snapshots | journal | system` declaring the architectural plane.
* **Invariant 3 (Idempotency of GET Endpoints):** All `GET` requests except `/journal/queue` must be completely non-destructive and side-effect free. Destructive queue operations remain confined to `/journal/queue`.

---

### 3. CI-Enforceable Quality Gates and Conventions

To prevent architectural drift and ensure strict adherence to API standards across future PRs, the following automated checks are codified into `tests/architecture/test_api_standards.py` and executed via `.venv/bin/python scripts/verify.py`:

1. **Router Path Naming Convention Enforcement:**
   * All endpoints registered in `ed_telemetry.adapters.driving.api.server.TelemetryHttpHandler` must match the canonical regex:
     `^/api/v1/(state|status|snapshots(/[a-zA-Z0-9_-]+)?|journal/(latest|query|stream|queue)|system/(health|watcher|logs|control))$`
     or belong to the explicit `DEPRECATED_LEGACY_ROUTES` tuple.
2. **OpenAPI Schema Synchronization Gate:**
   * Every canonical route present in `server.py` must exist as an operational path in `architecture/api/openapi.yaml`.
   * Any undocumented router path will fail the CI test suite.
3. **Mandatory Header Verification Gate:**
   * Automated HTTP test fixtures assert that all responses contain valid `X-Telemetry-Source` and `X-Telemetry-Plane` header values.

## Consequences

### Positive
* **Deterministic Head Immediacy:** `/telemetry/head` provides instantaneous state in < 1ms, completely isolated from SQLite ingestion throughput and historical backfills.
* **Intuitive Developer Experience:** Endpoint paths reflect their natural domain (`status`, `snapshots`, `journal`, `system`).
* **Zero Data Ambiguity:** Injected `X-Telemetry-Source` headers provide unmistakable clarity regarding transient memory vs. persistent database storage.
* **Automated Guardrails:** Pre-commit and CI gates prevent arbitrary route additions and enforce OpenAPI synchronization.
* **Seamless Compatibility:** All existing integrations continue functioning via legacy route aliases.

### Negative / Trade-offs
* **Temporary Route Aliasing:** `TelemetryHttpHandler` must maintain dispatch mappings for both canonical and legacy routes until the next major release.
